# squad-engine

Ядро баллистики Squad на Rust для SquadCalc. English version: [README.md](README.md).

* **Решатель** (`flight`, `weapon`): замкнутые формулы в `f64` для обеих дуг, фаз ускорителя
  (ConstantAcceleration), ограничения `MaxSpeed`, смещений дула и пределов возвышения; полёт считается кадрами
  выделенного сервера по 1/49.87 с, ускоритель работает `ceil(T / dt) - 1` из них (правило и источники - в
  `flight.rs`). Перенесён из `src/js/squadBallistics.js` и `src/js/squadFiringSolution.js` и удерживается тестом
  паритета, который запускает настоящие JS-классы. Перенесено: полёт (`height_at`, `path_at`, `apex`), `peak_angle`,
  поиск корней с отсевом по дулу (корень, который дуло уже прошло, не выстрел) и тёплым стартом от корней соседа
  (`SolveHints`), `max_range` и проверка траектории по профилю местности (`Flight::above` и `RangeMax`). Не
  перенесено: разброс, урон, вероятность попадания и отрисовка страницы, а также объект JS `trajectory` как таковой
  (его `height`, `at` и `above` - это `height_at`, `path_at` и `above`). Оружие хранит таблицу разгона своих
  ступенчатых полётов между решениями (`Weapon::flight`).
* **Сегменты траектории** (`path`): полёт в виде прямых отрезков, вершины которых лежат точно на траектории.
* **BVH** (`bvh`): построение binned SAH, развёртка в формат со skip-указателями (ниже), импорт и экспорт `bvh.bin`.
* **Запросы** (`trace`): Мёллер-Трумбор отрезок/треугольник в `f64` (эталон) и `f32` (паритет с GPU, опционально
  SIMD128), безстековый обход (первое попадание), проверка линии огня по всей траектории.
* **Карта высот** (`heightmap`): сэмплер 16-битных G16 с правилом диагонали треугольников как в игре.
* **Воксельные колонки** (`voxel`): чтение файла `VCOL1` (`tools/volumetric/py/codec.py`) и запрос отрезка обходом
  колонок по DDA (первый занятый воксель или чисто), см. [Воксельные колонки](#воксельные-колонки-vcol1).
* **Уточняющий проход** (`precision`): вокруг одной цели воксельный обход решает то, что далеко от геометрии, а точные
  треугольники региона в 150 м (`RTRI1`) - то, что подходит к ней ближе margin, см.
  [Уточняющий проход](#уточняющий-проход-rtri1).
* **JSON-интерфейс** (`io`), CLI (`squad-cli`) и wasm-экспорт (`wasm`, feature `wasm`) с ES-обёрткой в `js/`.

Система координат движка: метры, **X на восток, Y на север, Z вверх**. Азимут отсчитывается по часовой стрелке от
севера (`atan2(dX, dY)`). В Unreal ось Y направлена на юг: переведите координаты до построения BVH и до вызова.

## Формат BVH (`bvh.bin`)

Формат является контрактом с WGSL-обходом. Все числа little endian.

```
bvh.bin
  u32 node_count
  u32 tri_count
  node[node_count]       по 32 байта
  triangle[tri_count]    по 48 байт

узел (32 байта)                          треугольник (48 байт) = 3 x vec4<f32>
  смещ.  0  f32 min.x                      смещ.  0  f32 x0, y0, z0, 0   вершина 0
         4  f32 min.y                             16  f32 x1, y1, z1, 0   вершина 1
         8  f32 min.z                             32  f32 x2, y2, z2, 0   вершина 2
        12  u32 a
        16  f32 max.x
        20  f32 max.y
        24  f32 max.z
        28  u32 b
```

* Узлы идут в порядке обхода в глубину. Первый потомок внутреннего узла - следующий (`index + 1`), правый потомок
  находится по escape-индексу левого.
* `a` - **escape-индекс**: куда идти, если луч не попал в коробку узла или поддерево закончилось. `0xFFFFFFFF` -
  конец обхода. Для узла `i` это всегда `i + размер_поддерева(i)` (у листа `i + 1`), а `0xFFFFFFFF`, если результат
  равен `node_count`. У корня `0xFFFFFFFF`.
* `b` у **листа** равно `(first_triangle << 8) | triangle_count` (`1..=255` треугольников), у **внутреннего** узла
  равно `0`. Лист определяется условием `(b & 0xFF) != 0`.
* Треугольники хранятся в порядке листьев: лист `L` владеет `triangles[first_triangle .. first_triangle + count]`.
* Пустая иерархия: `node_count = 0`, `tri_count = 0` (8 байт).

Безстековый обход:

```
i = 0
while i != 0xFFFFFFFF:
    node = nodes[i]
    if луч попал в коробку узла (t in [0, t_max]):
        if node.b & 0xFF:                       # лист
            проверить треугольники node.b >> 8 .. + (node.b & 0xFF); при попадании уменьшить t_max
            i = node.a
        else:
            i = i + 1                           # в первого потомка
    else:
        i = node.a
```

**Ограничение: 2^24 треугольников на один `bvh.bin`.** `first_triangle << 8` должно помещаться в `u32`, поэтому
один файл адресует не более 16 777 216 треугольников. `BvhSet` делит большую выборку по пространству (медиана по
длиннейшей оси центроидов) на несколько иерархий именно такого формата (`bvh_000.bin`, ...); их коробки могут
перекрываться, запрос обходит все части, в корневую коробку которых входит луч. 72 098 154 треугольника Фаллуджи
превращаются в 8 частей. Один такой `bvh.bin` потребовал бы ещё 3,5 ГБ под треугольники, что выше стандартного
`maxStorageBufferBindingSize` в WebGPU.

Углы коробок - точные `f32`-координаты вершин (без запаса); `f64`-запрос расширяет коробки на 1e-6 м. Лист содержит
до 4 треугольников, если дальнейшее деление не выгодно по SAH (16 корзин на ось, стоимость обхода 1, стоимость
треугольника 1); при числе больше 255 деление обязательно.

## JSON-интерфейс

Запрос:

```json
{
  "weapon_specs": { "v0": 110.0, "mass": 4.1, "drag_coef": 0.47 },
  "pos_gun": [0.0, 0.0],
  "pos_target": [0.0, 600.0, 0.0],
  "environment": { "z_scale": 100.0, "heightmap_ref": "map.png", "bvh_buffer_ref": "bvh.bin" }
}
```

Ответ:

```json
{
  "firing_solution": { "azimuth_deg": 0.0, "elevation_mrad": 253.7 },
  "flight_data": { "time_sec": 5.63, "max_ordinate_meters": 38.9 },
  "occlusion_status": "clear",
  "collision_details": { "point": [0.0, 600.0, 0.0], "material": "unknown", "lethality": 1.0, "splash_footprint_radius": 0.0 }
}
```

* `drag_coef` (и `mass`) **принимаются и игнорируются**: снаряды Squad летят в вакууме, `g = 9.80 *
  ProjectileGravityScale`, без сопротивления.
* `pos_gun` - `[X, Y]`, высота орудия берётся из карты высот в этой точке (без карты 0). `pos_target` -
  `[X, Y, Z]`. `azimuth_deg` лежит в `[0, 360)`.
* `environment.z_scale` - половина диапазона высот карты: `Z = (v / 65535 * 2 - 1) * z_scale` для 16-битного
  отсчёта `v`. `heightmap_ref` и `bvh_buffer_ref` - имена ресурсов, загруженных хостом (CLI считает их путями к
  файлам: `.png` 16-бит grayscale или сырой `.g16` для карты; `bvh.bin` или каталог частей `*.bin` для BVH). Оба
  необязательны: без карты земля на Z = 0, без BVH линия огня не проверяется на препятствия.
  `environment.heightmap_resolution_m` (по умолчанию 1) - шаг отсчётов для CLI.
* `environment.vcol_ref` - имя воксельных колонок (для CLI путь к `.vcol`, gzip или уже распакованный). Путь
  трассируется через них как через BVH; попаданием считается ближайшее из вокселя, треугольника и рельефа. **Координаты
  тогда в системе файла** (Unreal: Y на юг), см. [Воксельные колонки](#воксельные-колонки-vcol1).
* `environment.region_ref` - имя региона уточнения (для CLI путь к `.rtri`), требует `vcol_ref`: внутри квадрата региона
  путь, подошедший к вокселю ближе margin, проверяется треугольниками региона вместо блокировки вокселем, см.
  [Уточняющий проход](#уточняющий-проход-rtri1).
* Сетка карты: строка 0 - северный край, `X = col * resolution`, `Y = -row * resolution` (`lng` и `-lat` в
  SquadCalc). Каждый квадрат делится на два треугольника по диагонали `(row, col)` - `(row + 1, col + 1)`, как в
  `src/js/squadHeightmaps.js`; точка дальше чем на полотсчёта за сеткой имеет высоту 0. Сырой `.g16`: `u32` ширина,
  `u32` высота, затем `u16` отсчёты little endian, строка 0 первой.
* `elevation_mrad` - возвышение прицела в миллирадианах (как `elevation_rad` решателя, умноженное на 1000). `null` и `occlusion_status: "no_solution"` - цель недостижима.
* `occlusion_status`: `clear`, `occluded` (путь встречает треугольник BVH, занятый воксель или рельеф до цели; рельеф проверяется
  с шагом карты, по 3 м у обоих концов не учитываются, как в SquadCalc), `unchecked` (нет ни карты, ни BVH, ни воксельных колонок),
  `no_solution`.
* `collision_details.point` - первое препятствие на пути, а при чистой линии огня - цель.
* **`material`, `lethality` и `splash_footprint_radius` - заглушка** (`materials.rs`): данные о семантике столкновений
  ещё не переданы, поэтому любая поверхность `"unknown"`, летальность `1.0`, радиус пятна `0.0` м. Точка вызова уже
  получает попавший треугольник; менять нужно только `materials::lookup`.
* Дополнительно: `weapon_specs.model` (ускоритель, `max_speed`, дуло, пределы возвышения, см. `weapon::Weapon`; его
  `velocity` заменяется на `v0`) и `options` (`arc`: `auto` | `low` | `high`, по умолчанию `auto` - нижняя дуга,
  если орудие может её дать; `tolerance_m`: допуск сегментов, по умолчанию 0.05).

CLI: `cargo run --release --bin squad-cli -- request.json` (или запрос в stdin) печатает ответ.

## Сборка и тесты

Тулчейн зафиксирован в `rust-toolchain.toml` (ставится `rustup` на пользователя, без sudo).

```sh
cargo fmt --check
cargo clippy --all-targets --features threads -- -D warnings
cargo test --release --features threads            # модульные, CLI, случайный BVH, паритет с JS-решателем
```

`tests/parity.rs` запускает под Node `tools/js/reference.mjs` (настоящие `Weapon` и `SquadFiringSolution` этого
checkout с заглушками из `tools/direct_fire`) на сетке `tools/direct_fire/compare.py` - 155 снарядов, 19 дальностей x
9 высот плюс 18 случаев у максимальной дальности - и сравнивает обе дуги, угол прицела, оба времени полёта, время
удержания и максимальную дальность. Кроме них: 8 дальностей от 10 см до 5 м x 7 высот в несколько метров (цели, которые
дуло уже прошло, и цели на собственной линии ствола) и 924 траектории против профилей местности (`above`, с `RangeMax`
и без). Допуск: 1e-9 градуса для углов, 1e-9 с для времени; для полётов дольше 10 с допуск относительный 1e-9 (почти
вертикальные высокие дуги близких целей, где время меняется примерно на 5e3 с на радиан, а `sin`/`cos` двух libm
различаются в последнем бите).

этих записях). BVH с точным ответом не расходился ни разу.

## Воксельные колонки (`VCOL1`)

Браузер не вместит коллизионные треугольники карты (Фаллуджа: 5,7 ГБ BVH), но вместит её воксельные колонки (статика
Фаллуджи 0,5 м x 0,25 м: 3,4 МБ gzip, 3,7 МБ с листвой; 4,7 МБ с прежним построителем по решётке выборки). `voxel::VoxelColumns::from_bytes` читает файл `tools/volumetric/py/codec.py`
(формат описан там; gzip или уже распакованный; повреждённый файл - ошибка, не паника; gzip, который распаковывается
больше `voxel::MAX_VCOL_BYTES` (256 МиБ при 228 МБ у самого большого из 58 измеренных файлов), - ошибка до заполнения
памяти; для регионов то же делает `precision::MAX_RTRI_BYTES`, 64 МиБ при 48,6 МБ). Воксель `(column, row, z)` -
полуоткрытый бокс `[min_x + column * cell, +cell) x [min_y + row * cell, +cell) x [z_min + z * dz, +dz)`; не более 4096
индексов высоты на колонку. Координаты любого запроса - в системе, в которой построен файл (Unreal: метры, X на восток,
**Y на юг**), так же как у треугольников BVH из `world_tris.py`: если вы работаете в системе движка, переведите их до
запроса.

`VoxelColumns::first_block(p0, p1)` возвращает первый занятый воксель, в который входит отрезок (`column`, `row`, `z`,
вход `t` в `0..=1`; `t = 0`, если отрезок начинается внутри) или `None`. 2D DDA (Amanatides-Woo) обходит клетки
`(column, row)`, которые пересекает отрезок; внутри клетки интервалы колонки проверяются по диапазону высот отрезка, а
вход считается в замкнутом виде, поэтому цена - число пересечённых клеток, а не вокселей. Виден каждый воксель, которого
касается отрезок (выборочный обход `models.py` перешагивает углы). Часть отрезка вне сетки не блокирует. `first_blocks`
считает много отрезков (rayon с `threads`), `first_block_along` - всю траекторию. `wgsl/voxel.wgsl` - тот же обход в
`f32` (см. `wgsl/README.ru.md`). Браузер: `Engine.loadVcol(ref, bytes)`, `Engine.voxelFirstBlock(ref, segment)`.

Модульные тесты: `src/voxel.rs` (рукотворные сцены; 5 000 случайных отрезков против slab-теста каждого вокселя),
`tests/voxel.rs` (файл, записанный `codec.py`, повреждённые файлы, CLI), `src/io.rs` (JSON-запросы), `js/test/`.

### На странице (слой объёмов)

`src/js/volumeWorker.js` загружает `public/engine/` (`npm run build:engine` собирает модуль и копирует туда `index.mjs`,
`pkg/squad_engine.js` и `pkg/squad_engine_bg.wasm`; страница собирается и работает и без него) и для активной карты два файла,
которые `tools/volumetric/py/publish_volume.py` кладёт рядом с высотной картой 1 м: `volume.vcol` (`VCOL1` этого раздела) и
`terrain.bin` (`TER1`, высоты одного рельефа с дырами ландшафта, `src/js/volumeTerrain.js`). Воркер стартует только если
пользователь включил настройку *Объёмы объектов на линии огня* и в `meta.json` есть запись `volume` (имена файлов, размеры,
sha256, сетка); карта без записи, отсутствующий движок или сбой загрузки оставляют высотную карту. Высоты страницы отсчитываются
от самого низкого уровня высотной карты (`z_min_m` в `meta.json`), в файлах лежит Z игры.

* Линия огня (`SquadFiringSolution.getObstacle`): траектория дискретизируется через метр, как проверка по высотной карте
  (по 3 м с обоих концов пропускаются), каждый отрезок проверяется `voxelFirstBlock`, каждая точка против рельефа. Проём здания
  пропускает выстрел (открытое окно, проём: дверь открыта или отсутствует), закрытое окно и стена непроницаемы. Пока воркер не ответил, действует результат по высотной карте.
* Зона огня (`SquadCoverage` через `SquadVolume.coverage`): для каждого луча воркер сэмплирует рельеф и верх вокселей под каждым
  отсчётом (вертикальный `voxelFirstBlock`), классифицирует с рельефом в роли профиля и проверяет траекторию, идущую ниже верха
  сооружения, по отрезкам (`squadCoverageRays.clearsStructures`). Цели в дыре ландшафта или вне ландшафта считаются вне зоны.
  Стена тоньше шага отсчётов (1-3 м), попавшая между двумя отсчётами луча, не видна, как и в высотной карте.

* Высоты цели (`SquadVolume.heightsAt`, сообщение воркеру `column`): воркер пробирует колонку вокселей в позиции цели от 1 м под
  рельефом до 120 м над ним (один `voxelFirstBlock` на центр вокселя) и возвращает пересекаемые твёрдые тела;
  `src/js/targetHeights.js` превращает свободные промежутки между ними в этажи (верх тела со свободными 1,8 м и более над ним),
  потолки, крышу, окна и дверные проёмы (свободный промежуток, у которого по обе стороны луча вдоль X или Y в пределах 0,75 м
  есть твёрдое тело; проём, если человек проходит, от 1,8 м). Эвристика по форме колонки, а не данные игры о зданиях. Выбранная
  высота становится высотой цели в `SquadFiringSolution`, а линия огня проверяется до самой точки цели (на 0,1 м выше пола или
  крыши, ниже потолка) вместо остановки за 3 м.

* Укрытие в зоне поражения (`SquadVolume.coverZone`, сообщение воркеру `cover`): `squadDamage.damageField` выполняется в
  воркере с ландшафтом (`terrain.bin`) вместо высотной карты и вокселями как `objects`: солдат укрыт, если его скрывает ландшафт
  (заметание горизонта, как раньше) или если `voxelFirstBlock` находит воксель между взрывом и им на том же участке линии,
  что и трасса по высотной карте (от 1 м от взрыва до 0,5 м до центра тела солдата, 0,9 м над ландшафтом). Стена укрывает
  солдата, открытый проём или окно - нет, пробитие не считается. Снаряд падает на высоте цели (выбранный для неё этаж, окно
  или крыша, иначе высота высотной карты у цели), а солдаты стоят на ландшафте, поэтому солдат на верхнем этаже не рисуется.
  Строка «выстрелов до поражения» во всплывающем окне (`hitProbability`) по-прежнему читает высотную карту. Зона, посчитанная
  без слоя или когда воркер не может ответить, - как прежде по высотной карте. Тесты: `tests/squadDamage.test.mjs` (`objects` с
  обратным вызовом) и `tests/volumeLayer.test.mjs` (сообщение `cover` через настоящий движок: солдат за стеной укрыт, на линии
  с проёмом - нет); в браузере `tools/browser_check/heatmap_check.mjs`.

Пробитие не считается (решение владельца от 2026-11-04). Тесты: `tests/volumeLayer.test.mjs`; в браузере
`tools/browser_check/volume_check.mjs` (репозиторий деплоя) на отрезках сверки Дженсена и Кокана.

### Тепловая карта позиций (обратная задача)

`src/js/positionHeatmap.js` отвечает на вопрос покрытия огнём, заданный наоборот: для выбранной цели (на выбранной для неё
высоте) с каких позиций на земле вокруг неё, в пределах дальности оружия, есть чистая линия огня до неё и насколько хороша
каждая позиция. Только оружие прямой наводки (с прицелом и MOA, `type: "directFire"`). Страничная часть -
`src/js/squadPositionHeatmap.js` (кнопка в диалоге цели, загружается по требованию, рисуется canvas-изображением поверх
карты, как покрытие), расчёт идёт в воркере слоя объёмов (сообщения `heatInit`, `heatRays`, `heatFinish` в
`volumeWorker.js`, `SquadVolume.positionHeatmap`) движком.

* **Позиции** лежат на лучах от цели (не менее 360, не более 1440, соседние лучи примерно в двух клетках друг от друга на краю),
  через каждые `cell = max(2 м, дальность / 160)` метров; дальность - оружия, не более 2000 м (баллистическая дальность
  оружия - десятки километров). Профиль ландшафта луча (высоты TER1, шаг 1-3 м) читается один раз на все его позиции.
* **Выстрел** - настильная траектория оружия из дульного среза стрелка, стоящего в позиции (с плеча, 1,5 м, если у оружия
  нет модели дульного среза или смещения по высоте), решённая так же, как в `SquadFiringSolution` и покрытии огнём
  (`squadBallistics.solveElevation`/`trajectory`: масштаб гравитации, разгон ракеты, пределы возвышения, время жизни снаряда).
  Позиция, где оружие нельзя навести или снаряд успевает исчезнуть, исключена (значение 0).
* **Линия огня**: ландшафт вдоль луча (первые и последние 3 м пропускаются, как везде), затем объекты: траектория ломаной с
  звеньями не длиннее 25 м (стрела прогиба самого медленного снаряда прямой наводки меньше 7 см), каждое звено проверяется
  `voxelFirstBlock`, а где у цели есть регион точности - `precisionFirstBlock`. Цель не на земле (этаж, окно, крыша)
  трассируется до точки в 0,5 м от неё, последнее звено оканчивается в самой точке. Позиция, где тело стрелка (вертикальный
  отрезок 0,3 м под дульным срезом) внутри вокселя, исключена. Открытые окна и проёмы - дыры, закрытые окна и стены - твёрдые,
  пробитие не считается (решения владельца от 2026-11-04).
* **Оценка** чистой позиции, от 0 до 1: `близость * зазор`, `близость = 1 - 0,6 * расстояние / дальность` (ближе лучше, самая
  дальняя сохраняет 0,4: дальний выстрел остаётся пригодным) и `зазор = 0,5 + 0,5 * k / 4`, где `k` из четырёх линий огня,
  смещённых вверх, вниз и в стороны на величину допуска, тоже чисты. Допуск - радиус разброса оружия у цели
  (`расстояние * tan(MOA / 2)`), не менее 0,5 м и не более 2 м, растёт линейно от дульного среза. Байт на позицию: 0 -
  исключена, 1 - закрыта, от 2 до 255 - оценка.
* **Регионы точности**: `volume.regions` в `meta.json` перечисляет опубликованные для карты файлы `RTRI1`
  (`tools/volumetric/py/publish_regions.py`, `{file, bytes, sha256, centre, radius, margin}`). Страница берёт регион, чей
  квадрат содержит цель дальше всего от своего края, не менее 50 м (точные треугольники покрывают не менее 50 м вокруг цели),
  загружает его как `<file>?v=<generated>`, проверяет sha256 и грузит в воркер, который строит иерархию треугольников
  (`Engine.loadRegion`); легенда пишет `Точные треугольники в N м вокруг цели, дальше воксели`, а если региона нет или он не
  загрузился - `Только воксели`. Файлы регионов есть только для целей, которые кто-то проверил: Jensen,
  `regions/region_221_-229.rtri` (1,93 МБ, 300 м x 300 м с центром в (221, -229)).

Тесты: `tests/positionHeatmap.test.mjs` (оценка, классификация, обратные вызовы, изображение, выбор региона),
`tests/volumeLayer.test.mjs` (воркер через настоящий движок на стене с проёмом), в браузере
`tools/browser_check/heatmap_check.mjs` (репозиторий деплоя).

Как читать:

* **Воксельный обход закрывает то, что задевает**: его ложно закрытые - линии, проходящие в пределах диагонали вокселя от
  угла или рамы (в основном в первых 50 м для окна, где рамы); регион точности убирает их все внутри своего квадрата.
  Немногие ложно чистые старого файла - треугольники, задевающие угол вокселя, потерянный построителем по решётке выборок; в файле точного вокселизатора их нет.
* **Исключённые позиции**: проба тела стрелка задаёт тот же вопрос, что и линия огня. Воксель помечается, когда его
  задевает треугольник, поэтому позиция у стены или под деревом может читаться как внутри него, хотя точные треугольники её
  не содержат; без региона так теряются 315 и 283 позиции, чистые по точному трассировщику, с регионом - ни одной внутри его
  квадрата. Оставшиеся 607 дальше 56 м, вне региона.
* **Лучи через окно узкие**: окно 1 м шириной со 100 м видно под углом 0,6 градуса, лучи стоят примерно через 1 градус, так что
  луч рисуется несколькими тонкими спицами (позиция между лучами берёт ближайший). Больше лучей - время растёт линейно;
  тепловая карта показывает, куда смотреть, а не таблицу стрельбы.
* **Только стрелки на земле**: стрелок стоит на высоте ландшафта (стрелок на крыше или верхнем этаже не спрашивается), на
  высоте дульного среза оружия.

## Уточняющий проход (`RTRI1`)

Воксельный обход ошибается так, как не лечится ростом файла: блокирует отрезок, вошедший в помеченный воксель, но
прошедший до диагонали вокселя от поверхности (ложно заблокировано, все его ошибки на файлах точного вокселизатора).
Прежний построитель по решётке выборок ещё и терял вокселы, и обход пропускал треугольники в них (ложно чисто); точный
вокселизатор их не теряет. Вокруг выбранной цели движок поэтому может перепроверить настоящими треугольниками. `precision::PrecisionRegion` строится из воксельных колонок карты и **файла
региона**:

* Регион - квадрат `центр +- 150 м` (X/Y, система файла вокселей) с треугольниками, блокирующими Visibility; файл
  строится офлайн из тех же шардов `world_tris.py`, что и воксели, скриптом `tools/volumetric/py/build_region.py`.
  Хранятся только треугольники, которые может задеть перепроверяемый отрезок: треугольник отбрасывается, если в
  пределах margin от его бокса нет занятого вокселя (под ландшафтом или вдали от любых вокселей), повторяющиеся
  треугольники хранятся один раз, вырожденные не хранятся.
* Отрезок режется по квадрату. Части **снаружи** отвечает воксельный обход. Часть **внутри** чиста, если остаётся дальше
  `margin` (по умолчанию 0,6 м) от любого занятого вокселя, и проверяется точными треугольниками, если подходит ближе
  (она пересекает воксели, увеличенные на margin, `VoxelColumns::dilated`; margin округляется вверх до целых вокселей:
  0,6 м - это 2 колонки и 3 по высоте на сетке 0,5 м x 0,25 м). Побеждает первое встреченное. Пробитие не
  моделируется.
* `PrecisionRegion::query` возвращает первое препятствие (воксель вне квадрата или треугольник региона) и признак,
  запускался ли точный проход; `first_block_along` обрабатывает всю траекторию. JSON: `environment.region_ref` рядом с
  `vcol_ref` (CLI: путь к `.rtri`; регион строится по колонкам `vcol_ref` того же запроса). WASM:
  `Engine.loadRegion(ref, vcolRef, bytes)`, `Engine.precisionFirstBlock(ref, vcolRef, segment)`.

```sh
# один файл на цель; шарды - вывод world_tris.py (см. tools/volumetric/README.md), margin записан в файле
python3 build_region.py map.vcol out/ --centre X Y --centre X Y --radius 150 --margin 0.6 statics.npz foliage.0.npz ...
```

Файл (`RegionFile`, gzip): квадрат, margin, начало квантования, общие вершины (шаг 0,1 мм, разности zigzag-varint,
нумерация по первому использованию) и индексы углов треугольников (разности zigzag-varint). Раскладка описана в
`precision::RegionFile`; `tests/precision.rs` проверяет, что писатель на Rust воспроизводит байты питоновского
построителя до gzip. Загруженный регион один раз строит иерархию треугольников (и увеличенные воксели своего квадрата).

Модульные тесты: `src/precision.rs` (все случаи прохода на ручных сценах, кодек файла, повреждённые файлы),

Как читать:

* **Смысл перебора margin изменился.** Со старым построителем margin был нужен, чтобы найти вокселы, потерянные
  сэмплингом (129 и 83 ложно свободно при margin 0, одно при 0,3 м на Kokan). С точным вокселизатором любой margin, включая
  0, точен на этих отрезках, потому что каждый воксель, которого касается треугольник, есть в файле: margin покупает только
  долю в точном проходе, 34 % при 0 против 45 % при 0,6 м. **0,6 м оставлен**, потому что уже опубликованные регионы
  (Jensen) собраны с ним и потому что файл, который отдаётся сегодня, всё ещё старый (по решётке выборок), а для него 0,6 м
  - наименьший из проверенных margin без неверных ответов; когда отдавать начнут точные файлы, margin 0 (примерно на
  четверть меньше перепроверок и файл региона меньше) даст те же ответы на этих отрезках. С регионами 150 м это не
  запускалось и здесь не меняется. Эти отрезки нетипичны: 70 % из них начинаются в 3 м от занятого вокселя, так что
  высокая доля мало говорит о настоящей тепловой карте.
* **Когда треугольники есть везде, проход точен** на этих отрезках (0 неверных при любом margin), касательные включены;
  раньше при margin 0 исчезали только ложные блокировки (отрезок должен войти в воксель, чтобы его перепроверили), а
  129 / 83 ложно свободно оставались.
* **Что остаётся при регионе 150 м** - геометрия вне квадрата: часть отрезка дальше 150 м от цели отвечают одни воксели
  (если цель в начале, точен другой конец: 0 + 9, 1 + 106 и 0 + 31 неверных). Больший радиус стоит размера файла, меньший -
  точности. На Fallujah, где регионы по 150 м содержат 1,8 - 7,3 М треугольников, после прохода неверно 0,43 %
  (0,17 % без касательных), а прогон с целью в начале оставляет 31 неверный отрезок.
* **Цена**: на Jensen и Kokan 1,4-1,6 от времени воксельного обхода на отрезок в одном потоке (3,8 -> 6,2 мкс, 7,8 -> 10,6 мкс;
  машина общая, считайте порядком величины; в старом прогоне 1,1-1,7), плюс файл: 0,1 - 5 МБ gzip на Jensen, 1 - 3,5 МБ на
  Kokan, 6,5 - 26 МБ на Fallujah (медиана 15,9 МБ: плотный город сильно отличается от двух других карт), и одна сборка
  иерархии на загруженный регион (секунды для самых плотных, до 13 с на Fallujah, в wasm дольше). Доля в точном проходе на
  Fallujah 60 %. Воксельный файл остаётся единственной загрузкой на всю карту.

## WebAssembly

```sh
cargo install wasm-bindgen-cli --version 0.2.130 --locked    # один раз
sh js/build.sh        # js/pkg (обычная) и js/pkg-simd (SIMD128-проверка треугольников)
node --test "js/test/*.test.mjs"  # загружает wasm в Node
```

`js/index.mjs` - ES-обёртка (`loadEngine`, `Engine.solve`, `loadBvh`, `loadHeightmap`, `loadVcol`, `firstHit`,
`voxelFirstBlock`, `buildBvh`, `segmentTriangle`). SIMD128-сборка - тот же код с `-C target-feature=+simd128` и feature `simd`; тест в Node проверяет,
что она даёт те же `f32`-результаты бит в бит, что и скалярная.

Потоки: feature `threads` включает rayon (параллельная сборка BVH и пакетные запросы) в нативной сборке. В браузере
нужны `SharedArrayBuffer`, то есть cross-origin isolation (`Cross-Origin-Opener-Policy: same-origin` и
`Cross-Origin-Embedder-Policy: require-corp`, настраивает владелец сайта), и feature `wasm-threads`
(`wasm-bindgen-rayon`), для которой нужен nightly с atomics и `-Z build-std`; такая сборка **не входит в закреплённый
stable-тулчейн и здесь не собиралась и не запускалась**.

## Замечания к модели

* Сегменты траектории не интегрируются: каждая вершина считается по точной формуле полёта (парабола, ускоритель
  вдоль оси, ограниченный участок, либо шаги игры для ускорителя вдоль траектории, как в JS), участок
  делится, пока его середина не окажется в пределах `tolerance_m` от хорды. Апекс всегда вершина. Допуск проверяется
  в середине каждого участка после первого деления на 8 равных частей.
* Запрос повторяет `reference.py`: отрезок `p0 + t (p1 - p0)`, `t` из `[0, 1]`, попадание на рёбрах и с любой
  стороны; отрезок с `|det| <= 1e-12` параллелен и промахивается.
