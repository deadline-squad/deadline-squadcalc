# engine/wgsl - WebGPU-часть баллистического движка Squad

Два WGSL-шейдера читают BVH, который экспортирует Rust-ядро (`engine/`), плюс JS-хост и тесты на реальном
WebGPU-устройстве.

| Файл | Назначение |
|---|---|
| `bvh_common.wgsl` | Структуры BVH, привязки 1-2, `trace_closest()`: обход без стека, slab-тест + Moller-Trumbore. `gpu.mjs` дописывает его перед остальными шейдерами (в WGSL нет `#include`). |
| `trace.wgsl` | Точки входа `trace_segments` (один поток на отрезок) и `trace_trajectories` (один поток на траекторию из N отрезков, возвращает первый перекрытый). |
| `heatmap.wgsl` | Точка входа `heatmap`: один поток на кандидата-позицию стрельбы, обе дуги. |
| `voxel.wgsl` | Точка входа `voxel_segments`: один поток на отрезок, первый занятый воксель файла `VCOL1` обходом колонок по DDA (без BVH). |
| `gpu.mjs` | Хост: `parseBvh`, `requestDevice`, `BallisticsGpu` (`traceSegments`, `traceTrajectories`, `heatmap`). Работает в браузере и в любом WebGPU-рантайме. |
| `test/` | `make_fixture.py` (реальные треугольники Фаллуджи + точный эталон float64), `bvh_tools.mjs` (тестовый JS-экспортёр BVH и CPU-копии в f64), `run.mjs` (прогон). |

## Формат BVH (читается, не меняется)

`bvh.bin` = `u32 node_count, u32 tri_count`, узлы, треугольники, little endian.

* узел, 32 байта: `{ min.xyz f32, u32 a, max.xyz f32, u32 b }`
  * `a` - индекс выхода: следующий узел, если луч промахнулся по боксу или поддерево закончилось; `0xFFFFFFFF` - конец обхода.
  * `b` = `first_triangle << 8 | triangle_count` для листа (count 1..255), `0` для внутреннего узла, первый потомок которого - узел `index + 1`.
* треугольник: 3 x `vec4<f32>` (xyz, pad) = 48 байт, в порядке листьев. Номер треугольника в ответе - позиция в этом массиве.

Под `first_triangle` отведено 24 бита, поэтому один BVH адресует не более 16 777 215 треугольников.

## Привязки (group 0, одинаковая раскладка для всех трёх точек входа)

| binding | `trace_segments` / `trace_trajectories` | `heatmap` |
|---|---|---|
| 0 uniform | `Params` (32 Б: count, node_count, flags, tri_base, seg_per_traj, end_trim f32, 2 pad) | `HeatParams` (112 Б, см. комментарии структуры) |
| 1 storage, read | узлы | узлы |
| 2 storage, read | треугольники | треугольники |
| 3 storage, read | отрезки: 2 x `vec4` на отрезок (p0, p1; w не используется) | карта высот: u16, по два в u32, построчно |
| 4 storage, read_write | `SegmentHit` x count (32 Б: point.xyz, t, tri, seg, 2 pad) | `Cell` x 2 на кандидата (16 Б: state, clearance, weight, path fraction) |

`SegmentHit.t` - доля отрезка (`p0 + t (p1 - p0)`); при промахе `t = 1.0`, `tri = 0xFFFFFFFF`.
Для `trace_trajectories` поле `seg` - номер первого перекрытого отрезка внутри траектории, `0xFFFFFFFF` если путь свободен.

## Модель выполнения

* `@workgroup_size(64)`, один поток на элемент, линейный индекс `gid.y * num_workgroups.x * 64 + gid.x`; `gid.y` нужен, если групп больше 65 535 (4,19 млн элементов), хост делает это сам.
* Каждый поток пишет только в свой слот: без атомиков и гонок. Локальное состояние фиксировано (индекс узла, лучшее попадание, несколько векторов), стека и рекурсии нет. Цикл обхода ограничен `node_count` шагами.
* Боксы расширены на 1 мм; тест Moller-Trumbore двусторонний, порог `|det| <= 1e-12` как в `reference.py`.

## Тепловая карта

Для цели `(x, y, z)` и сетки кандидатов шейдер берёт высоту земли (билинейно, 16 бит,
`zMin + raw * (zMax - zMin) / 65535`), поднимает дульный срез на `muzzleHeight`, решает
`tan a = (v0^2 -/+ sqrt(v0^4 - g (g D^2 + 2 dz v0^2))) / (g D)` (низкая / высокая дуга; `g = 9.80 * масштаб гравитации`,
как в `squadFiringSolution.js`), режет вакуумную параболу `z(x) = x tan a - g x^2 (1 + tan^2 a) / (2 v0^2)` на `chords`
хорд (по умолчанию 32) и трассирует их. Хорды лежат под настоящей дугой (она вогнутая), поэтому «блокировано» слегка
пессимистично - не более чем на `g D^2 / (8 v0^2 chords^2)` метров. Нужно `g > 0`.

Поля ячейки: `state` 0 свободно / 1 блокировано / 2 недостижимо при `v0`; `clearance` - наименьший вертикальный зазор (м,
не более длины зонда, по умолчанию 20 м) между внутренней точкой пути и поверхностью BVH под ней (0, если блокировано);
`weight = D0 / (D0 + D)` (D0 = `distanceScale`; 1 над целью, 0,5 на D0, тяжёлый хвост - дальние позиции остаются годными);
`path fraction` - где на пути первое попадание (блокировано) или 1.

## Воксельное ядро (`voxel.wgsl`)

Самостоятельное (`bvh_common.wgsl` не использует). `f32` в локальных метрах сетки: хост вычитает начало сетки в `f64`
(это делает `VoxelGpu.traceSegments`). Обход тот же, что у `voxel::VoxelColumns::first_block` в Rust-ядре, см. README
движка.

| binding | содержимое |
|---|---|
| 0 uniform | `Params` (count, column_count, width, height, cell, dz) |
| 1 storage, read | идентификаторы колонок по возрастанию (двоичный поиск) |
| 2 storage, read | первый интервал каждой колонки (`column_count + 1` значений) |
| 3 storage, read | интервалы: пары `[start, end)` индексов высоты, два `u32` на интервал |
| 4 storage, read | отрезки: 2 x `vec4` на отрезок (p0, p1) |
| 5 storage, read_write | `VoxelHit` x count (16 Б: `t` f32, `column`, `row`, `z`; свободно = `column` `0xFFFFFFFF`) |

`parseVcol` (`DecompressionStream`) превращает файл в три массива, `VoxelGpu.create` загружает их.

## Лимиты и разбиение BVH сверх лимита привязки

* По умолчанию `maxStorageBufferBindingSize` в WebGPU - 128 MiB (134 217 728 Б); `requestDevice()` запрашивает максимум адаптера (1 GiB у адаптера SwiftShader в тестах; у обычных видеокарт 2-4 GiB). `maxComputeInvocationsPerWorkgroup` (>= 256) для 64 потоков не проблема.
* На одну привязку в 128 MiB помещается 4 194 304 узла (32 Б) или 2 796 202 треугольника (48 Б). Узлов 0,5-2 на треугольник при 1-4 треугольниках в листе, поэтому первым упирается буфер треугольников: около 2,7 млн треугольников на кусок на устройстве с лимитами по умолчанию.
* Разбиение: поделите набор треугольников по пространству (например kd-разрезом по границам сцены) на части, каждая из которых помещается, постройте по BVH на часть и передайте все в `BallisticsGpu.create` как `chunks`. `traceSegments` делает один проход на кусок над одним и тем же буфером `hits[]` с `flags = ACCUMULATE` и `tri_base` = число треугольников в предыдущих кусках: следующие куски лишь укорачивают `t_max` до найденного ближайшего попадания, результат равен одному BVH. Номера треугольников глобальные, в порядке кусков.
* Ограничения: `traceTrajectories` и `heatmap` используют только первый кусок (им нужно ближайшее попадание по всем кускам для каждой хорды), держите нужный район в одном BVH. Один BVH также ограничен 2^24 - 1 треугольниками из-за кодирования листа.

## Последний проверенный прогон

Полный вывод: `test/last-run.txt`. Устройство: headless Chromium WebGPU на программном адаптере SwiftShader (CPU; GPU на тестовом
сервере нет). Окно 100 x 100 м Фаллуджи, 1 574 368 треугольников, 1 048 575 узлов BVH, 20 000 случайных отрезков.

* GPU f32 против точного float64: совпало 19 979 из 20 000; 21 расхождение «попал/не попал», все скользящие (конец отрезка точно в
  центре треугольника либо линия не дотягивается до ребра не более чем на 1,5e-5 м). Других расхождений нет.
* Сам `reference.py` ошибается на 22 из 20 000 отрезков (список тайлов семплируется с шагом 2 м и может пропустить тайл, который
  отрезок задевает); арбитром служил перебор всех треугольников в float64, обход BVH в float64 с ним совпал на всех отрезках.
  Ещё 11 отрезков попадают в копланарные дубликаты с другим номером при равном t.
* `trace_trajectories`: 1 500 траекторий x 16 хорд, 0 расхождений с float64.
* Два куска с accumulate против одного BVH: 0 различий. Heatmap: 784 кандидата x 2 дуги, 0 расхождений с float64-копией.
* Скорость на SwiftShader: около 20 000 отрезков/с (диспатч 200 000 отрезков, только ядро). Это скорость CPU; на реальных GPU не измерялась.
* `naga` 30.0.1 принимает оба склеенных шейдера без предупреждений; tint в Chromium компилирует их с 0 сообщений.
* Воксельное ядро (`run_voxel.mjs`, Jensen и Kokan, по 100 000 отрезков): см. `test/last-run-voxel.txt` и таблицу в `engine/README.ru.md`. tint компилирует `voxel.wgsl` с 0 сообщений; сборка wasm совпадает с нативным DDA на всех отрезках; GPU против нативного f64 DDA расходится на 10 / 2 отрезках, все объяснены округлением `f32` на гранях вокселей; против точных треугольников ошибочны 1,43 % (Jensen) и 4,56 % (Kokan) отрезков без скользящих пар. Около 19 000 отрезков/с на SwiftShader (CPU).

## Тесты

```
python3 -I engine/wgsl/test/make_fixture.py <fallujah_tris.npz> ~/agl/tools/volumetric/py <dataDir> 20000 100 1   # нужен numpy
node engine/wgsl/test/run.mjs <dataDir>
```

`run.mjs` запускает headless Chromium (`playwright-core`, переменные `PLAYWRIGHT_CORE`, `CHROME`) с
`--enable-unsafe-webgpu --use-webgpu-adapter=swiftshader --enable-features=Vulkan,UseSkiaRenderer --use-gl=angle --use-angle=swiftshader`.
На этом сервере нет GPU и драйвера Mesa Vulkan; Chromium содержит SwiftShader (программный Vulkan на CPU), он даёт настоящее
устройство `navigator.gpu` (`architecture: swiftshader`). Скорость, полученная так, - это скорость CPU, не GPU. Переменная
`EXPORTED_BVH=/path/bvh.bin` прогоняет те же отрезки через файл Rust-экспортёра. Шейдеры дополнительно проверяются `naga` 30.0.1
на склеенных исходниках (`cat bvh_common.wgsl trace.wgsl > x.wgsl && naga x.wgsl`).

Воксельное ядро (сначала `sh engine/js/build.sh`; данные из `engine/tools/make_voxel_segments.py`, см. `engine/README.ru.md`):

```
node engine/wgsl/test/run_voxel.mjs <dataDir> jensen,kokan
```
